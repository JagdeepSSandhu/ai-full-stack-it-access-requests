# Assessment follow-up: evidence and proposed operating boundaries

This is a review and delivery proposal, not a certification or an implemented federal control. Northstar and its supplied requests are fictional; the assignment does not establish that this repository holds federal tax information, has an ATO, or is subject to a particular federal program. The TO52 federal requirements below are taken from the assessment's program context, not inferred from the Northstar materials or claimed to come from a studied source.

## Data and untrusted input in this project

The requester's and manager's names, team, system, permission, dates, business purpose and exact supporting quotes can reveal an employee's identity, job function and privileged access. In particular, joining the named requester to a production/admin request and its start/end dates can reveal who has privileged access and when; a credential-only redaction would miss that risk. Use the fictional fixtures for demonstrations and session captures. Before using actual customer records, the data owner must approve the processing purpose and destination, minimize or tokenize identifying fields before any prompt, evidence or log, and restrict access and retention for the source, SQLite history and exported snapshots. Preserve a protected mapping only in an authorized environment; do not commit it. If exact quotes are needed for review, keep them in that environment rather than publishing them as evidence. The current application sends the entire message to the configured live provider and stores source bytes and quotes locally; it does **not** implement this redaction or an authorization boundary. Do not use it with real sensitive records until those controls are supplied and verified.

Messages are untrusted: `access_requests/prompt.py` instructs the model to treat them as data, and the application validates the response and requires human review. A malicious message could still cause the model to omit or misclassify an override. Schema validity and quote matching do not prove resistance to injection; `planning/validation.md` records this limitation. Do not give source text authority to change routing, tools, policy or approvals. For sensitive deployment, enforce tool and network boundaries outside the model, and route suspicious or ambiguous requests to a human. Never treat the prompt alone as a security control.

## Conditional TO52 overlay: specific delivery handoff

Apply this overlay only if the customer and Cyber confirm the scenario. Classification and controls require the responsible domain's determination:

| Surface and boundary | Classification and trigger | Delivery requirement and owner |
|---|---|---|
| A hypothetical request includes a taxpayer name or TIN linked to a return, tax liability, filing status or information obtained from IRS tax administration. | Treat the linked identifiers and tax information as potentially §6103-protected return information pending authorized classification; an employee name or system name alone is not automatically §6103 data. | Data owner and privacy/Cyber: identify the actual protected fields and allowed recipients; require masking, restricted scope, access logging and retention controls. No real taxpayer text or reversible token map in prompts, commits, session logs or public artifacts. |
| A request or extracted record is saved, changed, exported or sent across an authorization boundary. | A persisted change to protected records is a regulated write in this scenario; sending source text from intake to an external model endpoint is a confidentiality-boundary crossing. | System owner and Cyber: inventory each write and outbound hop; authorize the destination and access path before use. The current live provider call and local stores are not evidence of authorization. |
| The service is within an ATO boundary. | ATO requirements attach to the deployed system and its actual components, not to a README. | ISSO/Cyber: map controls to the actual system and maintain the POA&M and authorization evidence; require Cyber sign-off before deployment or any protected-data use. Cyber sign-off is a gate, not an ATO or compliance determination. |
| A proposed hosted dependency lacks the required authorization for the system. | The customer must determine whether its authorization and contract permit the service and data flow. | Architecture/procurement and Cyber: substitute an authorized service or obtain the required authorization before use; no assumption that a vendor's status authorizes this specific use. |
| The human review interface is a covered Section 508 surface. | Accessibility applies to the actual delivered interface and use context, as determined by the accessibility owner. | Accessibility owner: conduct keyboard and screen-reader passes and document defects and remediation before release. |

Partition physically by distribution rights: a redacted, committable main segment contains synthetic fixtures, code and sanitized evidence; a separately protected sensitive segment is terminal, with no path back to the main segment or to agent context. Do not rely on model instructions, statistical filtering or a 99% success rate: 99% is a failing grade for this near-zero residual-risk objective. Prevent the agent from simultaneously holding protected data, attacker-controlled instructions and an exfiltration channel. Cut the cheapest leg: a taxpayer-data environment must have no network reach to external destinations, enforced outside the agent and verified by the infrastructure owner. Approved tools only, least privilege and an explicit allowlist apply; a configurable endpoint is not an allowlist. The safety backstop must exist and be verified **before** autonomous work with protected data; refuse or stop when the backstop is missing or unverifiable. These are proposed requirements, not claims that this repository enforces them.

A concrete Codex-style example is a locked-down sandbox with only the redacted workspace mounted, no access to the sensitive segment or network, and approval required for any scope expansion or write outside the sandbox. Infrastructure must enforce and test that configuration; the agent must not be able to loosen it itself. The federal acts and sign-off requirements come from the program context, not from the tool example.

Proposed agent-in-PR boundary: the agent may inspect and edit only the redacted workspace, run approved offline checks and propose a diff. It may not fetch customer data, access the sensitive segment, call an external model with protected information, change security or approval settings, deploy, merge, grant access, or assert compliance. A human maintainer reviews the diff and evidence; Cyber signs off on the applicable security controls before release or protected-data use, and the designated authorizing official makes any authorization decision. No autonomous merge or production write. Done means a human-reviewed diff, passing scoped checks, documented data flows and control gaps, the control map/POA&M where applicable, accessibility evidence where applicable, and required Cyber sign-off recorded by its owner.

## Evaluation plan and honest evidence

Evaluate a change to the harness before adding it. Use the same fictional request and initial commit for two independently reset runs in one evaluation session: control uses the existing prompt and checks; treatment adds a proposed instruction-override routing rule. Keep model, reasoning level, inputs, tool permissions and output budget fixed; alternate arm order across several paired trials. A separate adaptive attacker sees the defense and iteratively rewrites a synthetic request to induce an unauthorized route or instruction-following. Keep a held-out set of attacks for the final comparison, and report both successful attacks and failed/invalid runs.

A machine-checkable `done.sh` for this experiment should fail unless the output is schema-valid, retains the original document identity, makes no tool or network calls outside the allowlist, and routes every labeled override in the held-out set to human review. Compare attack success rates and the paired difference, with counts and per-pair results; use human judgment for whether preserved quotes faithfully capture the attack and whether the diff is clear and maintainable. Record time, retries and variance; flag non-repeatable results as flaky. Any observed failure becomes a concrete regression case and the specification for a tool/interface fix, then rerun the paired comparison. A successful benchmark is not proof of security against unknown attacks.

No such paired experiment has been run for this follow-up, so there is no measured lift or defensible baseline to report and no added harness architecture is licensed by this plan. Existing mock scores in `verification.md` measure the fixture-backed extraction pipeline, not the effect of a harness change or an adaptive adversary. The actual human owner must inspect the resulting diff for unnecessary complexity and duplication and decide whether it is maintainable for the next operator; passing tests establish neither that judgment nor federal compliance.
